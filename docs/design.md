# Дизайн JobPool

## Задача

В одном namespace создаётся слишком много Job, и они съедают ресурсы кластера. Нужно ограничить число
**одновременно активных** Job в namespace через CRD и контроллер.

Условия:
- лимит действует только в том namespace, где создан `JobPool`;
- в одном namespace — не больше одного `JobPool`;
- считаются **активные** Job: завершённые место не занимают.

## Общая схема

```
kubectl create job
   → API server: аутентификация, RBAC
   → mutating webhook mjob.kiribu.dev     есть JobPool в namespace? → suspend: true + label queued
   → etcd
   → контроллер JobPool                    активных < max? → первые из очереди: suspend: false, снять label
   → Job-контроллер Kubernetes создаёт поды
```

## Решения

### D1. Job сверх лимита ставится в очередь, а не отклоняется

Если отклонять, повтор ложится на каждого клиента: человека, CI, другие операторы. С очередью вся логика внутри
оператора: клиент создаёт Job как обычно, и она **в конечном итоге** выполнится. Это естественная для Kubernetes
модель: система сама доводит состояние до желаемого.

### D2. Очередь — это `spec.suspend`

`suspend: true` при создании — Job существует, но поды не создаются. `true → false` — Job стартует. Встроенный
механизм, ничего своего не нужно. Важно: `false → true` у **работающей** Job убивает её поды, поэтому паузим только
новые Job и Job, которые ещё не запущены.

### D3. Паузу ставит mutating webhook, а не reconcile

Контроллер видит Job, когда она уже в etcd. Встроенный Job-контроллер видит её в тот же момент и сразу создаёт поды.
Это гонка, которую мы можем проиграть. Webhook меняет Job **до** записи в etcd, и Job-контроллер видит её уже на паузе.

### D4. Webhook паузит все новые Job, решает только контроллер

Если бы webhook сам считал свободные места, два параллельных запроса оба увидели бы «2 из 3» и пропустили бы обе Job:
работает 4 при лимите 3. Контроллер же обрабатывает `JobPool` последовательно (один reconcile на ключ, плюс
leader election). Одна точка принятия решения, webhook без состояния. Цена — небольшая задержка до старта, даже
когда место есть.

### D5. Webhook проверяет, есть ли `JobPool` в namespace

Без пула Job проходит без изменений, иначе она зависла бы на паузе навсегда. Namespace берётся **из admission-запроса**,
а не из объекта: в манифесте `metadata.namespace` может не быть (`kubectl apply -n x`). Удаляемый `JobPool`
(`deletionTimestamp`) считается отсутствующим.

Пул читается из кэша: webhook стоит на пути каждой Job и должен отвечать быстро. Кэшу webhook верит, только если
там живой пул. В двух случаях кэш этой реплики может отставать, и webhook один раз спрашивает API server напрямую:

- **пула в кэше нет** — его могли создать долю секунды назад;
- **в кэше пул с `deletionTimestamp`** — старый `default` мог уже удалиться, а на его месте появиться новый (другой
  UID). Если поверить кэшу, Job прошла бы мимо очереди нового пула.

Оба случая бывают только в момент создания или удаления пула: webhook вызывается лишь для namespace с label
(D14), поэтому лишний запрос редкий. Обратная ошибка безопасна: если кэш ещё показывает живой пул, которого уже
нет, Job встанет в очередь без пула, и контроллер её отпустит (D10).

### D6. Свои Job отмечаем label, чужую паузу не трогаем

Пользователь может сам создать Job с `suspend: true`, чтобы запустить её позже. Webhook такую Job не трогает. Нашу
паузу отмечает label `jobpool.kiribu.dev/queued=true`. Label, а не annotation, потому что по label можно фильтровать
(`List` с `MatchingLabels`). Очередь — это Job с этим label.

### D7. Активная Job = не на паузе и не завершена

У Job нет `phase`. Активна, если `spec.suspend != true` и нет condition `Complete`/`Failed` = True. По
`status.active` считать нельзя: у только что запущенной Job он какое-то время равен 0, и контроллер запустил бы лишнюю.
`spec.suspend` мы меняем сами, и это видно сразу. Учитываются **все** Job namespace, в том числе созданные до пула.

### D8. Порядок — FIFO

Сортировка по `creationTimestamp`, при равенстве по имени (у timestamp точность до секунды). Удаляемые Job из очереди
не запускаются.

### D9. Работающие Job сверх лимита не трогаем

Если активных уже больше лимита (запущены до `JobPool` или лимит уменьшили), пауза убила бы их поды. Просто ничего
не запускаем, пока активных не станет меньше лимита: `свободно = max(0, max − активные)`.

### D10. Удаление `JobPool` → finalizer распускает очередь

Без finalizer Job из очереди остались бы на паузе навсегда. Finalizer `jobpool.kiribu.dev/release-queue`:

```
status Ready=False, reason=Terminating
1. снять label enabled с namespace (webhook больше не вызывается)
2. снять паузу со всех Job с label queued
3. снять finalizer
```

Label снимается первым, чтобы новые Job перестали вставать в очередь. Но admission-запрос, который прошёл webhook до
снятия label, может сохраниться в etcd уже **после** шага 2: такая Job попадёт в очередь, которой больше нет. Повторная
проверка через секунду этого не гарантирует: у запросов «в полёте» нет известной верхней границы. Поэтому
контроллер следит за Job с label `queued` и **без** `JobPool`: событие о такой Job запускает reconcile
`<namespace>/default`, тот не находит пул и отпускает Job (D12). Это работает в любой момент, не только во время
удаления.

Новый `JobPool` во время удаления старого появиться не может: у него было бы то же имя (D11), а API server не создаёт
объект, пока старый с таким именем не удалён. Поэтому finalizer не проверяет «преемника».

### D11. Один `JobPool` на namespace — фиксированное имя `default`

`JobPool` может называться только `default`. Это CEL-правило в CRD: `self.metadata.name == 'default'`. Имена в
namespace уникальны, и второй `default` отклонит сам API server (`AlreadyExists`), атомарно, на уровне хранилища.

Первая версия использовала validating webhook: `List` пулов в namespace → отклонить, если уже есть. Ревью показало,
что этого мало. Проверка и запись не атомарны: два параллельных CREATE оба видят пустой namespace, и сохраняются оба.
Контроллер подстраховывал (главный — самый старый, второй получает `Duplicate`), но второй объект всё равно
существовал, а условие задачи — «не может быть больше одного». Кроме того, webhook пропускал новый пул, пока старый
удаляется, и finalizer старого мог распустить очередь при уже действующем новом лимите.

Фиксированное имя закрывает всё это без своего кода: нет validating webhook, логики «главного» пула и передачи
очереди. Цена — имя ничего не говорит, но пул в namespace и так один. Так же устроены другие объекты-одиночки в
Kubernetes, например ServiceAccount `default` в каждом namespace.

### D12. Reconcile будят `Watches()` + map-функции, а не `Owns()`

`Owns()` работает через `ownerReferences`, а Job создают другие. Сделать `JobPool` владельцем Job нельзя: при
удалении пула garbage collector удалил бы все Job. Имя пула известно заранее (`default`), поэтому любое событие
сводится к ключу `<namespace>/default`:

- `For(JobPool)` — создание, смена лимита, удаление;
- `Watches(Job)` — новая Job, завершение, удаление, смена паузы. Событие ставится в очередь, если в namespace есть
  пул (по кэшу) **или** у Job есть label `queued`: такую Job нельзя оставить на паузе без пула (D10);
- `Watches(Namespace)` — кто-то изменил label `enabled`. Событие ставится в очередь, если в namespace есть пул
  или стоит наш label: без пула label нужно снять.

Проверка «есть ли пул» в map-функции нужна, чтобы Job всего кластера не вызывали reconcile с запросами к API server.

Если пула нет, reconcile убирает следы: снимает label с namespace и отпускает Job с label `queued`. Перед этим он
проверяет отсутствие пула мимо кэша: пул, созданный долю секунды назад, кэш может ещё не видеть.

Webhook reconcile напрямую не дёргает: после него запрос ещё может отклонить кто-то другой. Реагируем на то, что
реально сохранено. Reconcile level-triggered: всё пересчитывается с нуля, поэтому склеенные или повторные события
не страшны.

### D13. Список Job читается мимо кэша

Кэш controller-runtime отстаёт от собственных записей контроллера, а потоки событий Job и `JobPool` независимы.
Сценарий: reconcile #1 запустил `A`, обновил status, status будит reconcile #2, а событие про `A` ещё не дошло. В
кэше `A` всё ещё на паузе, и если в очереди перед ней окажется новая `N`, запустится лишняя Job. Лимит нарушен.

Варианты: читать Job через `mgr.GetAPIReader()` (+1 запрос на reconcile) или expectations, как во встроенных
контроллерах (состояние в памяти, сложнее). Выбран первый: просто и очевидно корректно, а Job в пределах одного
namespace немного. Патч Job идёт с optimistic lock (`resourceVersion`): если Job изменилась, reconcile повторится на
свежих данных.

Кэш остаётся там, где устаревание безопасно или подстраховано: map-функции и webhook Job (если пула нет или он
удаляется, webhook идёт в API server, D5).

### D14. `failurePolicy: Fail` + `namespaceSelector` + `matchConditions`

| | `Ignore` | `Fail` |
|---|---|---|
| Оператор недоступен | Job создаётся без паузы и сразу стартует | Создание Job отклоняется |
| Цена | Лимит нарушен, и исправить нельзя: пауза убьёт поды | Клиент повторяет запрос (контроллеры делают это сами) |

Выбран `Fail`: гарантия лимита — смысл решения. Но webhook на Job во всём кластере с `Fail` при падении оператора
остановил бы создание Job везде, включая `kube-system`. Поэтому `namespaceSelector`: webhook вызывается только для
namespace с label `jobpool.kiribu.dev/enabled=true`. Контроллер ставит label, когда в namespace появляется `JobPool`,
и снимает в finalizer. Label принадлежит контроллеру: изменение вручную он сразу исправляет (D12). Проверка
`JobPool` в самом webhook (D5) остаётся второй линией защиты.

Webhook подписан и на UPDATE (D17), но `matchConditions` (CEL в конфигурации webhook) пропускает к нему только
снятие паузы. Остальные изменения Job (label, finalizer от garbage collector) от оператора не зависят и при его
недоступности не ломаются.

Лимит включается, когда API server видит label на namespace. Контроллер ставит label и сразу после этого пишет
`Ready=True`, поэтому в инструкциях после создания пула стоит `kubectl wait --for=condition=Ready`. Это не строгая
гарантия: `namespaceSelector` API server проверяет по своему кэшу Namespace (informer), который обновляется
асинхронно, обычно сразу, но без гарантированной границы (особенно при нескольких API server). Job, прошедшие до
этого, считаются как Job, запущенные до пула (D9). Строгая активация потребовала бы другого протокола; лишний
`sleep` её не даёт. Без `namespaceSelector` окна не было бы, но тогда `Fail` бил бы по всему кластеру.

### D15. Высокая доступность webhook-а

- 2 реплики менеджера: reconcile делает лидер, webhook обслуживают обе;
- readiness = webhook-сервер запущен (`StartedChecker`), трафик идёт только на готовые поды;
- `LeaderElectionReleaseOnCancel`: при остановке лидер сразу отдаёт lease;
- PodDisruptionBudget `minAvailable: 1` — drain не снимет обе реплики;
- `preStop: sleep 5s` — под, который удаляют, сразу выпадает из endpoints Service, но kube-proxy обновляет правила
  с задержкой, и запросы ещё какое-то время идут на него. Пауза перед SIGTERM даёт ему ответить на них, иначе при
  rolling update или drain Job отклонялись бы по таймауту (это поймал e2e со сменой лидера в CI). Действие `sleep`
  встроено в Kubernetes (GA с 1.34), shell в образе не нужен;
- мягкий anti-affinity — реплики по возможности на разных нодах;
- `timeoutSeconds: 5`, чтобы не вешать запросы.

### D16. Наблюдаемость

`status`: `activeJobs`, `queuedJobs`, `observedGeneration`, condition `Ready` с reason `Active` / `Terminating`.
Колонки `kubectl get jp`: Max, Active, Queued, Ready, Reason. Событие `Started` / `Released` на каждую запущенную Job.

### D17. Снять паузу в обход очереди нельзя

Webhook только на CREATE оставлял обход: `kubectl patch job x -p '{"spec":{"suspend":false}}'`. Job из очереди или
Job, которую пользователь сам создал на паузе, стартовала бы сверх лимита, и остановить её потом нельзя (D2).

Поэтому webhook обрабатывает и UPDATE: если паузу снимает **кто-то кроме оператора** в namespace с пулом, Job
возвращается на паузу и получает label `queued`. Для пользователя «снять паузу» значит «встать в очередь», Job
запустится, когда освободится место. Это тот же принцип, что в D1: не отказ, а очередь. Пауза, которую пользователь
поставил сам, по-прежнему не трогается, пока он её не снимает.

Оператора webhook узнаёт по имени пользователя в admission-запросе. Своё имя оператор узнаёт при старте через
`SelfSubjectReview` (то же, что `kubectl auth whoami`): в кластере это его ServiceAccount. Настраивать ничего не
нужно, но оператор должен работать под **своей** учёткой. При локальном запуске (`make run`) он берёт пользователя
из kubeconfig, и если тот же пользователь запускает `kubectl`, webhook примет его снятие паузы за действие оператора.
Для локальной разработки это допустимо, в кластере у оператора отдельный ServiceAccount.

## Известные ограничения

- **Leader election не даёт fencing.** client-go [прямо говорит](https://pkg.go.dev/k8s.io/client-go/tools/leaderelection#hdr-Overview),
  что два лидера могут работать одновременно. Сценарий: старый лидер построил план «запустить `A` и `B`» и завис
  дольше срока lease (15 с); новый лидер запустил другие Job; старый ожил и запустил `A` и `B`. Optimistic lock не
  спасает: он проверяет версию каждой Job, а не всего namespace. Итог — лимит превышен на размер устаревшего плана
  (до `maxConcurrentJobs` лишних Job), пока лишние не завершатся. Нужна пауза процесса дольше 15 секунд именно
  между планом и запуском; при штатной смене лидера (`ReleaseOnCancel`, удаление пода) этого не происходит. Строгая
  гарантия потребовала бы атомарного резервирования слотов в API server. Это общее ограничение операторов на
  controller-runtime, включая встроенные контроллеры.
- **Лимит считает Job, а не поды.** Одна Job с большим `parallelism` займёт много ресурсов. Задача — ограничить
  число Job; ресурсы ограничивают `ResourceQuota` и `LimitRange`, и они совместимы с `JobPool`.
- **FIFO с точностью до секунды.** У `creationTimestamp` точность в секунду; внутри одной секунды порядок по имени.
  Порядок стабилен, но для Job с `generateName` внутри секунды он не совпадает с порядком создания.
- **Недоступный оператор держит удаление `JobPool`** (finalizer) и namespace с пулом, пока оператор не вернётся.
  Это обычная цена finalizer.

## Отвергнутые альтернативы

| Альтернатива | Почему нет |
|---|---|
| Отклонять Job сверх лимита | Повтор ложится на каждого клиента (D1) |
| Ставить паузу в reconcile | Гонка с Job-контроллером: поды могут создаться раньше (D3) |
| Webhook со счётчиком | Параллельные запросы превышают лимит (D4) |
| ResourceQuota `count/jobs.batch` | Считает все Job, включая завершённые, и отклоняет, а не ставит в очередь |
| CEL для «один пул на namespace» по содержимому | CEL видит только сам объект, а не соседей; поэтому CEL проверяет имя (D11) |
| Validating webhook для «один пул на namespace» | Проверка и запись не атомарны: параллельные CREATE проходят оба (D11) |
| `Owns()` / `JobPool` владелец Job | Job не наши; GC удалил бы их вместе с пулом (D12) |
| Считать активные по `status.active` | Отстаёт сразу после запуска (D7) |
| Читать Job из кэша | Устаревший кэш нарушает лимит (D13) |
| Повторная проверка очереди в finalizer через 1 с | Не ловит запросы, сохранённые позже (D10) |
| Отклонять снятие паузы пользователем | Пользователь не смог бы запустить свою Job, пока есть пул; очередь честнее (D17) |
| `failurePolicy: Ignore` | Молча нарушает лимит при недоступном операторе (D14) |
| `Fail` без `namespaceSelector` | Падение оператора блокирует Job во всём кластере (D14) |

## Тесты

- `internal/jobpool` — табличные unit-тесты чистой логики (план запуска, FIFO, снятие паузы), покрытие 100%.
- `internal/webhook/v1` — envtest: запросы идут через настоящий API server и admission chain. Проверяются CREATE,
  снятие паузы пользователем и оператором (оператор — через impersonation), промах кэша и удаляемый пул в кэше.
- `internal/controller` — envtest с запущенным менеджером. Job-контроллера в envtest нет, завершение Job
  имитируется через `status`. Регрессии: CEL-правило имени, новый пул во время удаления старого, Job в очереди без
  пула, ручное изменение label `enabled`.
- `test/e2e` — kind: настоящие Job, поды, cert-manager, 2 реплики, смена лидера. Сценарии описаны в
  [e2e-guide.md](e2e-guide.md).
